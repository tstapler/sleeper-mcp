# Validation Plan: waiver-intelligence

**Date**: 2026-11-10

## Happy Path Scenario

Given a league with a warm unified transaction cache (a full-league GraphQL backfill already
recorded in `transaction_sync_runs`, including at least one historical `complete`-status waiver
bid at the target position), when the operator runs `sleeper waiver bid-projection --league
1352883872131481600 --player 3257 --roster 5`, then the CLI prints a suggested dollar bid grounded
in all five real signals (perceived value, league demand, bid history with sample size, claim
frequency, and FAAB-remaining with verified coverage) with zero browser launches — turning the
Baseline's "gut feel only" bid decision into a concrete, explainable number served entirely from
cache. Every other story in this plan is a variation on getting that cache populated and kept
correct (Phase 1/2), or on acting on what it tells you (Phase 4's edit/cancel), not a parallel
priority.

## Migration Test — `migration_should_be_reversible`

This repo's migrations are forward-only by convention (no down-script, `db.rs:150-160`'s own
precedent). "Reversible" here is scoped to what this plan's Rollback procedure actually promises —
**not** a literal up/down pair:

1. **Idempotent against an empty DB**: `StatsDb::open` against a brand-new tempdir path succeeds,
   and the `transactions` table has `status_updated`/`source` columns and `transaction_sync_runs`
   exists. Calling `StatsDb::open` a **second** time against the same path is a no-op (no error,
   same schema) — proves the `PRAGMA table_info` guard doesn't re-run `ALTER TABLE` and fail on an
   existing column.
2. **Additive-safe against a pre-existing old-schema DB**: manually create a `transactions` table
   with only the columns that existed before this feature (`transaction_id` ... through
   `roster_ids`/`waiver_bid`, no `status_updated`/`source`) and insert one row. Then call
   `StatsDb::open` against that file and assert: the new columns/table are added, the pre-existing
   row's data is untouched (`transaction_id`, `status`, `waiver_bid` etc. unchanged, new columns
   read back as `NULL`), and a second `open` call against the now-migrated file is again a no-op.
3. **Explicit scope note (do not over-claim)**: this test does **not** and cannot verify "an older
   binary still works against the new schema" — that requires literally running a prior binary
   build against a post-migration DB file, which isn't expressible inside a single `cargo test` run
   without checking out and compiling a previous revision. That guarantee rests on SQLite's own
   behavior (a `SELECT` that doesn't name the new columns is unaffected by their existence) plus the
   Migration Plan's own reasoning, not on this test — documented here rather than silently assumed
   covered.

## Test Stack

- **Unit**: Rust `#[test]`/`#[tokio::test]`, this repo's existing `FakeSession` seam double for
  browser-dependent tests. `claim_row_disambiguator`, `resolve_side`, `parse_league_transactions`,
  `StalenessTolerance::is_fresh`, and `BidProjection::render_short` are pure/no-I/O and get plain
  `#[test]` coverage inline in their own modules.
- **Note on a needed `FakeSession` extension**: two tests above
  (`league_transactions_via_seam_should_request_whole_league_scope_when_roster_filter_omitted` and
  `edit_cancel_claim_via_seam_should_resolve_and_cancel_when_fake_session_returns_two_claim_rows`)
  need capabilities `FakeSession` doesn't have today: capturing the JS string passed to
  `eval_string` (currently discarded as `_js`), and returning a *sequence* of distinct canned
  responses rather than one static string. Plan.md's own Task 1.4.1b already flags the second gap;
  the first is a new finding from this validation pass — both should be added to
  `src/browser/session/fake.rs` as part of implementing Epic 1.4/2.2, not invented ad hoc per test.
- **Integration**: `#[tokio::test]` against a real temp SQLite file (`StatsDb::open` on a tempdir
  path via the `tempfile` crate — no existing precedent for this in `src/db.rs` today, since it has
  no test module yet; this plan is the first to add one). CLI/MCP tests that exercise `read_through`
  end-to-end also fall in this category even where a `FakeSession` double covers their browser leg,
  because the dominant new risk surface is the real SQLite read/write path.
- **E2E / UX**: manual CLI/MCP invocation checklist (no GUI; no Playwright — this is explicitly out
  of place here). The live-UI selector bundle for Epic 4.2/4.3 and the Tuesday-waiver-window
  live-test both remain manual, operator-run checks per plan.md's own Wall-clock Blockers — no
  automated test can cover them in this sandbox.

## Coverage Targets and How to Measure

| Stack | Coverage command | Target |
|---|---|---|
| Rust | `cargo tarpaulin --out Stdout` | ≥80% line |

- All public service methods: happy path + error paths covered (see Requirement → Test Mapping —
  every one of the plan's 20 stories has at least one happy-path test and, where a meaningful
  failure mode exists, an explicit error-path test).
- All external integrations (`StatsDb`, `BrowserSession` seam, `SleeperClient`/REST): unit mocked
  (`FakeSession`/temp SQLite) + at least one integration test — satisfied for every story that
  touches `StatsDb` or the browser seam (17 of 20 stories; the 3 that don't — 1.4.1's pure
  disambiguator, 2.2.1's pure parser/query-shape tasks, 3.1.4's pure `render_short` — are
  deliberately I/O-free by design, per Pattern Decisions' type-driven-design rationale, so unit-only
  coverage is correct there, not a gap).
- UX acceptance criteria: every criterion in design/ux.md (43 surface-level + 8 testable
  feature-wide, excluding the explicit accessibility N/A) has a corresponding test above, either a
  new test or an explicit cross-reference to an existing one — never silently skipped.
