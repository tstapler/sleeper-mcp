# Pre-mortem: waiver-intelligence
**Date**: 2026-11-10

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The bid-projection tool's `suggested_bid` is a single confident-looking number built on a genuinely incomplete picture (no competing-roster FAAB visibility, `Floor`-confidence FAAB-remaining, thin bid-history samples), and Tyler anchors on it the way the Success Metrics intend — only the underlying picture is weaker than the number implies. | Tyler bids the suggested number, loses the claim to a much higher competing bid (or wins by overpaying far past what would have cleared), and only notices when he reviews the final winning bid after the fact. | Make `suggested_bid` refuse to render as a bare confident figure when `faab_remaining.confidence` is `Floor` or `bid_history.sample_size` is below a stated threshold (e.g. n<5) — the render should lead with the caveat, not the number. Fold the already-open adversarial-review Concern ("opponent-budget tiebreak awareness... dropped from Epic 3.1") into Phase 3 scope: at minimum surface league-wide FAAB-remaining alongside the target roster's own figure. | P1 |
| 2 | `upsert_transaction` writes and `record_sync_run` are two separate, non-atomic statements; nothing in the plan expires or re-checks a prior `Verified{as_of}` coverage row by age. A crash/partial sync after a prior full backfill leaves `has_full_league_graphql_coverage` still returning the *old* `Verified` timestamp, so FAAB-remaining keeps reporting `Verified` confidence even though the cache has since silently gone stale relative to real new transactions. | FAAB-remaining confidently reports `CoverageConfidence::Verified { as_of: <old timestamp> }` and a dollar figure that is missing transactions newer than that timestamp — looks authoritative, is wrong. | Add an AC (plan.md or validation.md) that `bid_projection.rs` treats `Verified{as_of}` as itself subject to a staleness check — e.g. `warn`/downgrade the signal to a caveat when `as_of` is older than the league's last known waiver-processing cycle (`waiver_day_of_week`), rather than treating "a full backfill happened once" as "the cache is current forever." | P2 |
| 3 | Edit/cancel row identity is disambiguated once at read time (`claim_row_disambiguator`) but never re-verified immediately before the click — an open architecture-review Concern. If the claims panel re-renders between read and click (another claim resolves, the DOM reorders), the click fires against the wrong row index. | Tyler asks to cancel claim A, the tool reports `Confirmed`, but a later check of the Sleeper app shows claim A is still pending and a *different* claim (B) was cancelled or had its bid changed instead. | Make the click-stage `eval_string` JS re-verify the target row's identity (e.g. compare a `data-transaction-id`/equivalent attribute, or re-run the disambiguation predicate) immediately before firing the click, returning `EditCancelOutcome::Ambiguous` if the re-check doesn't match the row resolved at read time — turn the architecture review's open recommendation into a stated Phase 4 acceptance criterion instead of an acknowledged-but-unaddressed gap. | P1 |
| 4 | Live-UI selector verification is gated on a wall-clock blocker (Tyler's own display, Tuesday-only waiver cycle) — only a few real pending-claim windows per month. The feature ships "implemented against `FakeSession`" but the first real invocation, under actual deadline pressure, either errors (selector not found) or produces an `Ambiguous` outcome Tyler doesn't trust yet, so he reverts to the Sleeper app by hand — the exact baseline behavior this feature was meant to replace. | The first live `sleeper waiver cancel`/`edit` call, run against a real time-sensitive claim, fails or returns an unverified outcome; Tyler opens the Sleeper app instead, and the next test opportunity is a week away. | Decouple selector verification from the real decision pipeline: validation.md should call for a deliberate low-stakes first trial (e.g. submit a throwaway $1 claim specifically to test cancel) before the feature is ever relied on for a claim that actually matters, rather than letting "first live use" and "first decision-critical use" be the same event. | P2 |
| 5 | This repo's own recommendation-discipline rule (adversarial critique + league context + external grounding before any real roster-money action) gates the *decision*, but nothing in the plan distinguishes that from gating the *projection lookup itself*. Under real waiver-deadline time pressure, the perceived overhead of "pulling up the tool" causes Tyler to just decide from gut feel instead — the baseline behavior this project exists to replace. | Weeks pass with a warm cache and a working bid-projection tool, but a check of `sleeper transactions` shows submitted bids that don't match any number the tool was ever asked to project — the tool existed but wasn't consulted before real claims went in. | Explicitly document (validation.md or the CLI/MCP tool descriptions) that `sleeper waiver bid-projection` / `project_waiver_bid` is a cheap, single-call read with no required ceremony attached to the lookup itself — the recommendation-discipline review applies only once a real bid is about to be submitted. Add a week-1 tripwire: did the tool get invoked before each claim actually submitted in that window? | P2 |

## P1 Items (address before implementation)
- [x] #1 — Resolved in plan.md: Story 3.1.4 now requires `render_short` to prepend a visible caveat
  marker (and set `low_confidence: bool`) when `faab_remaining.confidence == Floor` or
  `bid_history.sample_size < 5`; new Task 3.1.3b adds `competing_roster_faab` to `BidProjection`,
  folding opponent-FAAB visibility into scope rather than leaving it deferred. Covered by
  validation.md's `bid_projection_render_short_should_prepend_caveat_marker_when_faab_confidence_is_floor_or_sample_size_below_five`
  and `bid_projection_should_include_competing_roster_faab_when_other_rosters_have_positional_demand`.
- [x] #3 — Resolved in plan.md: new Task 4.2.1c requires the click-stage `eval_string` to
  re-assert the target row's identity in the same call that performs the click, returning
  `EditCancelOutcome::Ambiguous` on a mismatch. Covered by validation.md's
  `edit_cancel_claim_via_seam_should_return_ambiguous_when_row_identity_changes_between_read_and_click`.
